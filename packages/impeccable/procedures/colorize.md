# Refine color roles

Adapted from Impeccable `skill/reference/colorize.md` at `63b04e2530f5c7b41ea83c133daab24f34912456`, Apache-2.0. Modified for Pi: canonical color/accessibility owners replace duplicated thresholds and palette rules; automatic polish/live handoffs are removed. See package licenses and notices.

Follow [setup](setup.md) and [color](../references/taste/color.md). Preserve confirmed brand commitments and semantic meanings. A palette migration or identity replacement requires explicit scope; adding color does not authorize either.

Inspect actual tokens, assets, themes and representative states before choosing colors. Identify whether grayscale obscures hierarchy, where color alone communicates meaning, which foreground/background pairs need measurement, and whether data visualization has distinct requirements.

Name the intended relationship, emotional temperature, attention priority and color dosage. Define only consumed roles rather than a collection of unused swatches. Follow canonical rules for color notation, ramp construction, contractual brand colors, gamut and theme exceptions. Prefer the installed color library for computation; do not install or migrate one implicitly.

Apply changes consistently to the selected roles, preserving non-color cues and existing domain conventions. Measure actual rendered pairs including alpha, images, state and theme context where possible. Follow the accessibility owner for compliance; visual plausibility and static estimates are not conformance evidence.

Inspect light/dark, interaction, error, empty and dense states together, fix observed defects, then confirm at most once. Use setup's manual detector only on supported local files. Report measurements and their context, intentional exceptions and unverified rendering. Do not automatically launch polish or variant previews.
