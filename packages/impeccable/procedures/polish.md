# Polish the complete interaction path

Adapted from Impeccable `skill/reference/polish.md` at `63b04e2530f5c7b41ea83c133daab24f34912456`, Apache-2.0. Modified: canonical taste ownership, Pi tool boundaries, manual static detection and bounded verification replace upstream hook/storage handoffs. See package licenses and notices.

Polish is refinement, not concealed redesign. Preserve the incumbent visual world, factual copy, behavior and everything outside the requested scope. If the concept is wrong, report that separately rather than replacing it under the name of polish.

## Establish scope and evidence

Follow [target setup](setup.md). Establish the shipping constraints and inspect the whole requested path, not just its prettiest state. Use existing product context, representative shared components and adjacent flows to distinguish a local defect, missing reusable token, duplicated implementation or conceptual mismatch. Fix the cause at the narrowest correct level; do not invent abstractions for a single exception.

Use [principles](../references/taste/principles.md), [components](../references/taste/components.md), [motion](../references/taste/motion.md) and [accessibility](../references/taste/accessibility.md) as the rule owners. Do not introduce another set of numeric defaults here. Inspect layout, typography, color and copy against the actual project system; disclose any missing specialized guidance rather than claiming comprehensive coverage from the first slice.

## Triage and implement

Prioritize blocked tasks, misleading state, data loss and inaccessible paths; then missing loading, empty, error, success, disabled and permission states; then flow, hierarchy and responsive drift; then visual consistency and cleanup. Do not perfect one control while leaving the rest of the path incomplete.

Exercise realistic content, input methods, viewport sizes and failure states where available. Preserve neighboring navigation and save conventions. Keep imagery stable during loading and preserve meaningful names and labels. Ask before changing factual claims. Motion is not required merely to make a polish pass visible: apply the canonical input/frequency constraints before adding feedback.

## Verify and finish

Build the scoped change, inspect desktop/mobile and applicable input/state cases together, fix observed defects in one batch, then perform at most one confirmation round. Follow setup's explicit local detector path once where supported; a clean scan is not proof of design quality. If browser or device verification is unavailable, mark those cases unverified rather than pretending a source review exercised them.

Check functional completion, focus, semantics, zoom, content extremes, console errors, interaction latency and agreement with the existing system. Review the source diff for accidental churn, dead imports, duplicated styles and temporary artifacts. Report what changed, concrete verification results, intentional exceptions and remaining limitations. Do not launch another capability or agent as an automatic finish handoff.
