# Make one section bolder

Adapted from Impeccable `skill/reference/bolder.md` at `cd12f8660e2dde57b9615c8a6b8ea674101f9cfc`, Apache-2.0. Modified: Pi tool boundaries replace upstream handoffs, manual clarification and bounded verification replace upstream question-tool and polish-handoff automation. See package licenses and notices.

Bolder is amplification, not redecoration. Raise one named target to the conviction the rest of the page already implies. If a direction decision is still open, that is a separate conversation about foreign forms, not this command: this command refines a surface whose world already shipped. The reflex answer, reaching for more effects, is the opposite of bold; reject it first.

## Establish scope and evidence

Follow [target setup](setup.md). Run `node {{PKG_DIR}}/scripts/context.mjs`, adding `--target <path>` when the user names one, and inspect the whole page before touching the target. Note what the rest of the page does that the target section does not: the display type at full strength, the structural devices that carry meaning, the signature motif, the density and pacing. A flat section typically opts out of the system's own strongest moves; the reliable pass brings the target up to the expressive level its neighbors already reach, in the system's own vocabulary rather than a new one.

Use [principles](../references/taste/principles.md), [components](../references/taste/components.md), [typography](../references/taste/typography.md), [color](../references/taste/color.md) and [layout](../references/taste/layout.md) as the rule owners. If platform scope arises, native guidance is reported unavailable per setup.

## Amplify the target

Scope is sovereign. Touch only the named target and leave everything else literal: do not restyle neighbors, migrate the page to a new idea, or add colors, fonts, radii, shadows, or system primitives the surface does not already own. If the existing system genuinely cannot express the direction, stop and ask the user, naming the exact addition and the job it would do. Do not expand the system on your own.

Amplify what the system already owns: reuse its motif and type scale at full strength, turned up for this section rather than invented for it. The bolder version should look more like the same brand, not less. Keep content true and preserve existing claims unless the user supplies replacements; if real evidence is essential but absent, ask for it. Commit to one decisive move, then quiet everything around it so the move stays legible: if every element got louder, the section got flatter. Give the target its own rhythm, a peak in the scroll with a shift in density or pace, not more of the same.

Apply the skeleton test: strip the copy out of the planned section and study the bare structure. Hierarchy and the system's devices alone should still say what the section is and why it matters. A placeholder for an image or artifact names a job, an anchor and a piece of evidence, not a cue for decoration; fill that job with whatever the subject actually has.

NEVER:

- Restyle anything outside the named target.
- Introduce a new color, font, or system primitive without being asked.
- Change how existing actions or conventions in the section work.
- Cover weak structure with added effects or decorative media.
- Change factual claims without user-supplied replacements.

## Verify and finish

Build the change, inspect the target against its neighbors on desktop and mobile widths where supported, fix observed defects in one batch, then perform at most one confirmation round. Where the change touches a local web file, one optional detector pass is allowed: `node {{PKG_DIR}}/scripts/detect.mjs --json <local-file>` on local files only, never URLs, web-only. A clean scan is not proof of design quality. If browser or device verification is unavailable, mark those cases unverified.

Confirm everything outside the target is unchanged, no unasked primitive appeared, actions still work, and the section reads as the same brand, more sure of itself. Report what changed, concrete verification results, intentional exceptions and remaining limitations. Do not launch another capability or agent as an automatic finish handoff; naming `/impeccable polish` as a possible next step stays inline code, never an action.
