# Harness 最终设计：扁平规则与增量上下文

状态：已实现并通过包内验收（313 项测试、typecheck、pack、install、隔离 `pi --print` 加载）。运行时同时支持新 `rules` 格式与旧 `policies`/`skillPrompts` 读取路径（迁移期）。文本指导采用 `before_agent_start` 回合起始的持久化投递；同一轮内工具结果触发的 mid-run 即时投递是待验证的后续项（见 §8.4、§12.3）。自动 consolidation 子系统仍写旧格式、经旧读取路径消费，其向 `rules` 的迁移是明确的剩余工作。

> 一个扁平 `rules` 列表，三个明确的匹配入口，一套按身份覆盖的规则。
> 匹配负责决定何时适用，消息负责提供指导，Bash 的可选 `action` 负责增加执行条件。
> 上下文提示增量匹配、尾部追加、原位保留，按当前分支实际保留的消息去重。

验收契约：@packages/continual-learning/features/harness-rules-redesign.feature。

## 1. 问题与目标

旧设计将 `policies`、`disabled`、`skillPrompts` 分开管理：检查按名称覆盖，停用名单跨层累加，技能指导按技能名覆盖。规则身份、匹配条件和状态没有一致的含义。配置保存成功，也容易被理解为规则已经触发或要求已经执行。

新设计使用户能够直接回答五个问题：

1. 这是什么规则？由 `id` 标识。
2. 它在什么内容上匹配？由 `skill`、`bash` 或 `text` 指定。
3. 匹配后模型收到什么？由 `instructions` 或 `message` 指定。
4. Bash 是否需要额外执行条件？由可选 `action` 指定。
5. 当前采用哪一层定义，是否实际触发？由统一解析结果和运行记录说明。

界面、创建步骤与规则正文优先描述期望行为。自动处理保留精确语义，模型指导与确定性检查各自报告真实能力。

## 2. 领域术语

| 术语 | 定义 |
| --- | --- |
| 规则身份 | 跨配置层标识同一项约定的 `id`，与匹配目标独立 |
| 匹配入口 | 技能展开调用、Bash 调用、当前对话文字三者之一 |
| 有效规则 | 经过分层解析后获选的完整定义，包含来源与状态 |
| Bash 调用决定 | 一次调用的放行、等待确认或保持未执行的唯一决定 |
| 保留上下文 | 当前分支经过压缩、裁剪后，准备提供给模型的对话 |
| 指导消息 | Harness 根据有效规则提供的、模型可读的上下文消息 |
| 规则修订 | 有效规则规范化内容的内部摘要，用于识别内容变化；用户只维护 `id` |
| 投递记录 | 规则身份、修订、来源及其实际消息位置的关联，区分持久化与模型送达 |

## 3. 配置格式

### 3.1 完整示例

```json
{
  "rules": [
    {
      "id": "overlay-semantics",
      "skill": "open-deskos-widget",
      "instructions": "全屏弹出框表示弹层覆盖在底层界面之上。视觉与交互细节依据明确需求及项目规范确定。"
    },
    {
      "id": "push-result-guidance",
      "bash": "\\bgit\\s+push\\b",
      "message": "推送完成后，报告目标分支与远端结果。"
    },
    {
      "id": "review-push",
      "bash": "\\bgit\\s+push\\b",
      "action": "confirm",
      "message": "推送前确认目标仓库、分支与提交范围。"
    },
    {
      "id": "project-a-status",
      "text": "A项目|A 项目|Project A",
      "instructions": "项目状态：A 项目已弃用。回答相关问题时结合这一状态，当前工作以已确认的替代方案为准。"
    }
  ]
}
```

示例中的项目状态是演示数据，命令表达式是结构示例。真实配置使用用户确认的事实，并通过实际命令的正反例验证；单纯出现 `git push` 也可能是引用文字。

最小配置：

```json
{
  "rules": []
}
```

这表示本层没有新增或覆盖声明；其他层仍按优先级解析。

### 3.2 字段与合法组合

| 字段 | 类型与语义 |
| --- | --- |
| `id` | 必填非空字符串；准确、区分大小写的规则身份；同一文件内唯一 |
| `enabled` | 可选布尔值；省略等同 `true` |
| `skill` | 精确匹配已注册技能名 |
| `bash` | 对 Bash 原始 `command` 字符串进行正则匹配 |
| `text` | 对当前保留对话的文字进行正则匹配 |
| `instructions` | `skill`／`text` 规则必填的非空指导正文 |
| `action` | 仅用于 `bash`；省略、`confirm`、`block` 三种情况 |
| `message` | `bash` 规则必填的非空模型指导，同时用于解释执行决定 |

每条完整规则准确选择 `skill`、`bash`、`text` 之一。普通规则同时提供对应的完整正文。`confirm` 与 `block` 是一个字段的两个互斥值。

“空 action”使用省略字段表达；`null` 和空字符串得到明确校验提示。这样只有一种默认放行的写法。

停用继承规则可以只声明：

```json
{
  "rules": [
    {
      "id": "review-push",
      "enabled": false
    }
  ]
}
```

也可以保留完整、有效的规则内容并设置 `enabled: false`。恢复启用时使用完整定义。

顶层仅使用 `rules`。第一版不增加 `kind`、`when`、嵌套 `match`、独立 `disabled`、`observe`、数值优先级或自定义执行脚本。

### 3.3 匹配约定

- 技能名按完整字符串精确匹配；标点按名称原义处理。
- `bash` 与 `text` 使用非空 JavaScript 正则表达式源字符串，区分大小写，无隐含 flags。别名通过 `A项目|Project A` 表达。
- 正则逐个文本片段求值；任意一个片段匹配即可。不同消息或不同参数之间保持分隔，不通过拼接制造匹配。
- 正则不负责解释任意自然语言、shell 执行树或测试结果。
- 规则输入与正则执行均有可执行的资源限制。执行超时、取消或范围未完成是独立诊断，不当作“没有匹配”。长度限制本身不能保证正则运行时间；接入验收包括主线程保持可响应以及实际取消计算。

## 4. 配置位置与统一合并

优先级从低到高：

| 层 | 位置 | 默认用途 |
| --- | --- | --- |
| 内置 | 包内默认规则 | 基础规则 |
| 全局 | `~/.pi/agent/harness.json` | 当前用户的跨项目约定 |
| 项目共享 | `<project>/.pi/harness.json` | 项目默认创建与更新位置 |
| 项目个人 | `<project>/.pi/harness.local.json` | 用户明确选择的个人覆盖 |

实际 agent 目录采用 Pi 提供的目录解析；项目路径相对于当前项目会话。个人文件如需不被 Git 跟踪，创建流程检查项目已有忽略设置并报告结果，文件名本身不等于 Git 忽略保证。

### 4.1 唯一规则

> 同名规则就近完整替换，不同规则独立继承。

`id` 使用跨入口的统一命名空间。配置解析先决定每个身份的获选声明，再验证其定义与运行环境支持状态。匹配发生在解析之后。

| 当前层操作 | 有效结果 |
| --- | --- |
| 省略某个 `id` | 继承上一层 |
| 提供同名完整定义 | 使用本层全部字段 |
| 提供 `enabled: false` | 该身份停用 |
| 更近层提供完整启用定义 | 该身份重新启用 |
| 删除覆盖声明 | 恢复上一层定义 |
| 提供空 `rules` | 本层不作覆盖 |

完整替换也适用于省略字段：项目规则省略 `action`，表示放行并发送消息，即使外层同名规则是 `block`。外层的正文、动作和匹配条件均不隐式补入。

同名定义可以通过显式更新改变入口；预览展示这一变化。自动 consolidation 另受修改权限约束，不借助优先级取得变更权限。

数组顺序仅用于存储阅读；结果与投递采用稳定的 `id` 顺序，顺序本身不决定权限，也不解决自然语言冲突。

### 4.2 配置错误

- 不存在的文件表示该层未配置；其他读取错误有明确诊断。
- 对可识别 `id` 的无效声明，保留该身份的覆盖事实，显示无效原因；其他独立规则继续解析。逐条无效不使用旧修订快照，也不恢复外层同名定义。
- 无效条目若含 `bash`，或无法准确归入唯一入口，则 Bash 配置覆盖不完整，本次 Bash 调用保持未执行并请求修复。此规则在首次加载和热更新时一致。只含明确 `skill`／`text` 入口的无效条目影响对应指导，Bash 仍按其完整有效规则求值。
- 未注册技能表示该有效规则在当前环境不可用，外层同名定义继续被覆盖。
- 重复 `id`、损坏 JSON、未知顶层结构或无法识别身份的条目属于层级结构错误。热更新仅在这种整层无法解释的情况下，保留最近一次可解析、身份无歧义的层快照，并标记快照过期。快照包含当时已知的无效和停用状态，不因缓存而恢复更早版本；首次加载没有快照时明确显示该层未应用。
- 写入使用严格验证：所有候选条目和有效合并结果通过校验后，才原子替换文件。现有无效内容的修改需要明确授权。
- “默认放行”是正常求值的结果，不是配置或求值失败的别名。Bash 在配置覆盖不完整且没有可用快照、快照本身含影响 Bash 的无效身份、或求值失败时，返回配置／求值待处理状态。其他无关工具继续可用。
- 状态和测试报告说明使用的是当前文件还是上次解析快照；过期快照不能作为新配置验证成功的证据。

## 5. Bash：匹配就提供消息，动作决定执行条件

### 5.1 单规则行为

| `action` | 命令处理 | 模型上下文 |
| --- | --- | --- |
| 省略 | 正常执行 | 实际工具结果加规则 `message` |
| `confirm` | 用户批准后执行一次 | 调用决定、规则 `message`，以及存在时的实际结果 |
| `block` | 本次调用保持未执行 | 未执行状态、规则 `message` |

消息是基础能力，记录是内部可观测性。两者均不需要一个 `observe` 动作。

省略动作的例子：

```json
{
  "rules": [
    {
      "id": "push-guidance",
      "bash": "\\bgit\\s+push\\b",
      "message": "推送完成后，报告目标分支与远端结果。"
    }
  ]
}
```

这份指导随工具结果提供给模型，用于后续生成。提交给工具的命令已确定；需要先调整命令时，使用 `block` 返回具体调整建议，或使用 `confirm` 取得本次批准。

### 5.2 多规则汇总

先收集全部匹配规则及消息，再作出一个调用决定：

| 匹配情况 | 唯一决定 |
| --- | --- |
| 无匹配 | 正常执行，无附加规则消息 |
| 所有匹配规则省略动作 | 正常执行，提供全部消息 |
| 存在 `confirm`，其余为省略动作 | 合并为一次确认 |
| 存在 `block` | 保持未执行，提供全部匹配消息 |

多条确认规则合并原因。确认与阻止规则同时匹配时，最终决定为保持未执行，不进入确认界面。每条规则的动作互斥，不同规则可能同时匹配；上述汇总消除结果歧义。

### 5.3 确认与真实结果

- 确认绑定调用身份、完整执行参数、工作目录及有效规则快照。
- 界面展示待执行内容和全部确认原因；默认 60 秒取得明确决定。
- 批准只对展示的那次调用有效。重复发起的调用重新求值。
- 参数或规则快照在执行前变化时，重新求值，需要时取得新批准。
- 拒绝、超时、取消或缺少确认界面时，返回对应的未执行原因及所有匹配消息。
- 放行只是通过 Harness 检查，后续工具和其他权限检查仍按各自规则执行。
- 规则正文使用独立、可识别的附加部分进入工具结果；原生输出、错误状态、截断信息及已有执行细节保持原义。消息不是伪造的 stdout 或执行成功证明。
- 命令执行失败时也携带匹配消息。已阻止的调用不再运行 Bash，也不把指导重复投递成另一轮对话。
- 并行工具调用按各自调用身份关联消息；一个调用的确认与结果不作用于其他调用。

范围为模型发起的 `bash` 工具调用。用户手工终端、Pi 的 `!`／`!!`、其他命令工具和脚本内部子进程不自动变成本模式的检查入口。

## 6. Skill：技能调用范围内的补充指导

运行流程：

1. 识别 Pi 实际展开的技能调用与准确技能名。
2. 收集所有匹配、启用且有效的规则。
3. 在该调用开始生成前，将指导作为带来源的消息追加到对话末尾。
4. 按调用身份去重，记录投递结果。

同一次调用经过多次生命周期处理，每条规则只投递一次；后续新的技能调用可以再次收到指导。消息正文明确适用于该次技能任务，历史中的技能名不会重新启动技能入口。

读取 `SKILL.md` 只是文档读取。技能注册证明支持该选择条件，真实展开调用测试才证明触发。

技能指导采用对话消息而非修改 system prompt。历史保留不提升其权限或扩大适用范围；模型是否遵循仍由任务结果验证。

## 7. Text：对话内容触发项目知识与提示

### 7.1 配置

```json
{
  "rules": [
    {
      "id": "project-a-status",
      "text": "A项目|A 项目|Project A",
      "instructions": "项目状态：A 项目已弃用。讨论现状时明确这一状态；历史分析按相应时间背景解释。"
    }
  ]
}
```

这是用户选择的第三个入口：按正则匹配当前模型可见的全部保留对话，而非只匹配最新用户消息。

它负责及时提供配置中的状态，并不从关键词推断状态，也不自动查询事实。状态由用户或经证据与权限验证的配置更新维护。

### 7.2 精确扫描范围

在每个用户回合的 agent start（`before_agent_start`）取得一份匹配快照，扫描当前分支经压缩处理后的保留对话加上本次用户 prompt（机制与限制见 §8.4）。覆盖：

- 当前与历史中保留的用户文字、助手正文。
- 所有工具已完成结果中的模型可见文字，不仅是 Bash 结果。
- 模型可见工具调用参数中的字符串值，逐个值匹配。
- 当前保留的压缩摘要、分支摘要。
- 其他扩展提供的模型可见文字消息，包括仅在界面隐藏的消息。

扫描依据是当前分支经过上下文处理的模型输入，而非完整 session 文件。其范围不包含：

- system prompt、工具定义、内部 thinking、图片／音频二进制及签名。
- 消息 ID、工具结果 `details`、usage、时间戳等未作为文字发送的元数据。
- 已丢弃的原始历史、其他分支、被排除的 `!!` 输出。
- 工具截断输出所指向、但尚未实际读取进入上下文的文件内容。
- Harness 自己提供的指导、更新／撤销通知，以及 Bash 结果中 Harness 附加的消息部分。原始工具结果仍参与匹配。

各文本片段独立求值，跨片段不构造单个正则输入。可见结果超过 2,000 字符时依然扫描全部可见正文，不能借用压缩摘要序列化的截断范围。

匹配使用追加前的同一快照：A 规则的指导文字不能在本轮触发 B 规则。将规则正文与工具原文分开的来源信息由运行时维护，不靠查找普通文本标记猜测。

全文匹配的自然结果是：早先讨论的项目仍可能触发提示，否定句、引用和代码示例也可能匹配。文本入口匹配文字，不执行语义相关性判断。用户／模型后来引用指导、摘要改写指导时，文字可能重新成为普通匹配来源；本设计不承诺消除所有间接反馈。

## 8. 上下文追加、去重与缓存

### 8.1 基本不变量

> 每个用户回合的 agent start 检查新增需求；已投递的指导作为持久化消息保留在原位，新指导只追加到末尾。

设 `H` 是已有对话，`G` 是首次命中的指导，`A` 是助手响应，`T` 是完整工具结果批次：

```text
请求 1：H + G
请求 2：H + G + A + T
请求 3：H + G + A + T + 新消息 + 新指导
```

这样，在 system prompt、工具定义、provider 序列化与其他处理不变时，原有请求序列保持共同前缀。扫描本身不改变前缀。

被替代的临时重建方案会将第二次请求变成 `H + A + T + G`，在旧 `G` 的位置发生分歧。本设计不把既有指导移到每次请求的末尾，也不以每轮 system prompt 修改承载动态指导。

这保证 Harness 自身的序列稳定性，不承诺缓存必然命中或消除上下文 token 成本。压缩、切换模型、其他扩展和 provider 缓存策略仍会影响缓存。

### 8.2 去重粒度

| 入口 | 去重单位 |
| --- | --- |
| Skill | 技能调用身份 + 规则身份 + 规则修订 |
| Bash | 工具调用身份 + 规则身份 + 规则修订 |
| Text | 当前分支仍保留的最新投递／撤销状态 + 规则身份 + 规则修订 |

Text 不使用“整个会话曾经触发”的集合。是否已送达，以当前分支实际保留的带来源消息为证据。

同一轮新匹配的多条 text 规则可以组成一个追加消息，各条身份与修订仍可独立追踪。同一关键词出现多次只导致一次规则投递。

### 8.3 更新、撤销与生命周期

| 情况 | 行为 |
| --- | --- |
| 首次匹配，当前上下文无有效投递 | 尾部追加指导 |
| 相同修订已有有效投递 | 保留原位，不追加副本 |
| 内容更新且仍适用 | 尾部追加新版，明确替代该身份的旧指导 |
| 停用、删除后无继承替代、或适用条件改变后确定不再适用 | 对当前仍存在的旧指导追加一次失效通知 |
| 同名获选定义无效 | 追加一次失效通知，说明先前指导不再代表当前有效配置；显示该身份的校验诊断 |
| 正则超时、取消或匹配尚未完成 | 保持现有投递状态，报告判断未完成；本轮未获证据的匹配／失效转换等待下次成功求值 |
| 整层结构错误而使用上次解析快照 | 沿用该快照的定义、诊断与投递状态，并显示配置过期；没有快照时先前指导进入配置状态未知，追加一次状态通知而不冒称已验证有效 |
| 删除覆盖后显露另一层定义 | 按显露的定义判断更新或失效 |
| A 修订更新为 B，再恢复 A | 与最新状态 B 比较，追加 A；历史上曾有 A 不等于当前仍有效 |
| 停用后重新启用相同修订 | 与最新失效状态比较，匹配时重新追加启用指导；旧投递记录不抑制这次恢复 |
| 压缩移除了可识别投递，保留文字仍匹配 | 在新上下文末尾补入当前指导一次 |
| 关键词和指导都已离开保留上下文 | 当前无需投递 |
| 切换分支、fork、resume | 从当前分支重建状态，不借用其他分支的投递记录 |
| 模型请求重试或扩展 reload | 根据已保留消息去重，不因进程内集合重置而重复 |

配置错误导致的失效通知与成功匹配是两个独立事件；失败或取消的匹配不改写已确认的投递状态，整体请求已取消时也不为通知额外启动生成。

失效通知是来源明确的上下文说明，不表示能让模型“遗忘”已见内容。原始历史保持可追踪；确需移除旧文本时，通过明确的上下文重置／压缩处理，并接受相应前缀变化。

摘要中恰好出现相似句子，不构成某修订已投递的证据。摘要属于可匹配的当前文字，但不替代精确投递记录。每次准备只处理一次有限增量，不因新增指导或通知递归发起下一轮匹配。

### 8.4 消息位置与调度（已实现机制）

投递使用 `before_agent_start` 返回的**持久化自定义消息**，而不是临时的 `context` 钩子返回。原因：Pi 的 `context` 返回值只用于构造当次请求（`emitContext` 克隆后交给本次 LLM 调用），不写回对话状态；用它投递会导致每次请求重复追加、无法去重、且前缀在旧指导位置分叉。`before_agent_start` 返回的消息经 `appendCustomMessageEntry` 持久化到分支，因而天然满足保留、去重与前缀稳定。

- 求值时机：每个用户回合开始（agent loop 启动）一次。扫描面是 `buildSessionContext()` 的保留对话（含历史用户／助手文字、已完成工具结果、压缩／分支摘要、工具调用字符串参数）加上当前 `event.prompt`。
- 投递位置：作为该回合的持久化消息追加在用户消息之后、模型生成之前；一经写入即保留在原位，后续回合只在末尾追加新增／更新／失效部分。
- 去重依据：扫描保留对话中本模块此前投递的 `harness-guidance` 消息的 `details.entries`（按 id 记录 revision/status），据此判断 active/update/retired；不依赖进程内集合，因而 resume、fork、reload 后仍准确。
- 保持 tool call 与 tool result 的协议顺序；指导是独立消息，不插入未完成的调用批次。
- 规则命中本身不启动额外模型轮次。

**已知限制（诚实标注）：** `before_agent_start` 不在每次工具后的生成前触发，因此**同一轮内**由工具结果首次引入的关键词，要到下一个用户回合的 agent start 才被投递。设计早期设想的"工具批次之后、同轮下一次生成之前"的 mid-run 即时投递，需要 Pi 在请求准备 seam 提供可验证的持久化即时投递能力；在公开扩展接口确认支持之前，本实现采用回合起始投递，并把 mid-run 即时性标为待验证的后续项，而非声称已实现。

| 内容 | 主要承载位置 |
| --- | --- |
| 项目通用工作约定 | 项目指导文档 |

运行时读取配置遵循项目信任设置。外部文档和工具结果只提供匹配依据；注入正文来自已授权配置，不将命中文字自动拼接成高权限指令，不将关键词出现视为修改规则的授权。

指导作为带来源的对话内容提供，保留既有指令优先级。公司项目状态、语义规范与测试约定均需要真实来源；配置存在本身不是事实证明，也不是模型遵循保证。

输出／artifact 检查、任意工具参数检查和全局文件隔离不属于新核心。配置写入自身的结构、路径与事务保护属于内部完整性机制，单独实现，不作为第四个用户规则入口。

## 11. `/harness` 创建、状态与自动学习

### 11.1 创建或更新步骤

1. 确定 `skill`、`bash` 或 `text` 入口；识别更适合项目指导的要求。
2. 准确记录匹配对象和期望行为，使用描述性的稳定身份。
3. 选择默认项目共享文件，或用户明确指定的个人／全局文件。
4. 读取该目标，保留已有条目；目标不存在时使用 `{ "rules": [] }` 初始化。
5. 构造最小候选定义，校验匹配器、正文和有效合并结果。
6. 展示覆盖、停用和是否被更近层遮蔽的结果；提示本次是否改变执行条件。
7. 验证目标与相邻正常场景，原子保存并回读。
8. 在安全测试环境验证实际触发，分别报告保存、解析、投递和执行结果。

对于潜在副作用命令，先以不执行命令的求值用例验证，再用受控 fixture 验证真实调用路径；验证不等于在用户仓库执行示例命令。

### 11.2 状态展示

每条规则展示：身份、入口、匹配条件、启用／停用／无效／不可用状态、获选来源、被覆盖来源、动作及验证证据。

例如：

```text
project-a-status
入口：text · A项目|A 项目|Project A
状态：启用
来源：项目 .pi/harness.json
投递：当前分支已保留此修订
验证：历史文字与工具结果触发用例通过
```

验证记录绑定规则修订；配置更新后，旧记录只证明旧修订。模型指导报告“已送达”，不等同“已遵循”。Bash 放行与命令成功分别报告。

运行时新增提示采用简短生命周期行，展开显示正文、身份与来源。模型收到完整正文；TUI 使用 Pi 原生主题与 pi-kit 渲染，确认使用已有用户输入界面。普通未匹配调用保持原有显示。

### 11.3 自动学习

自动 consolidation 写入项目共享层。父进程验证事实证据、目标范围、正反例、所有权以及应用前后结果，再原子应用；子进程只提案。

自动新增需检查所有层、所有入口中的身份冲突，包括停用和无效声明。人工、全局、个人和内置定义的修改走明确授权。自动更新仅作用于当前仍由父进程追踪且内容一致的自有条目；入口切换、重新启用和执行条件放宽需要显式决定。

从项目指导提取到 Harness 时，验证适用范围保持一致。整个项目的 CM5 测试规范不因恰好存在某个技能就变成该技能专属指导。

## 12. 实现决策与接入门槛

### 12.1 模块与 interface

- 配置解析模块拥有读取、结构校验、按身份覆盖、正则编译、来源与诊断。
- 规则求值模块根据同一有效配置处理技能、Bash 和文本快照，返回匹配及调用决定，不执行命令。
- 上下文投递模块拥有消息身份、修订、分支状态、尾部追加与去重。
- Pi 适配器负责生命周期、真实消息／工具结果交付与确认 UI。
- 创建、状态与 consolidation 共同消费解析结果，不各自实现另一套合并逻辑。

这些模块通过一个小的运行时 interface 提供配置说明、事件求值和投递计划。测试跨越与实际调用方相同的 seam；Pi 的已注册事件和最终模型请求是首选验收位置。纯解析内部可以独立测试，但不替代生产入口验证。

### 12.2 Pi 接入的已知事实

本次设计研究核对了安装环境的 Pi 0.85.1：

- `before_agent_start` 支持返回持久化消息，适用于初始用户／技能调用；它不覆盖每次工具后的生成。
- `context` 在代理循环的模型生成前提供上下文副本。返回新增消息只证明本次请求被转换，不自动持久化或保留原位。
- `tool_call` 可以决定调用是否执行；`tool_result` 可以保留原生结果并附加消息。
- session 自定义元数据不自动进入模型上下文；界面隐藏的自定义消息仍可以进入模型上下文。
- 已完成工具后的 session 持久化，与运行中 agent loop 实际使用的消息数组，并非可以无条件视为同一更新。
- steering 可以进入下一次生成，但可能影响继续执行的调度；仅有一次 `sendMessage` 调用不能证明满足本设计。

### 12.3 接入能力的验证结果与剩余门槛

已验证并采用：`before_agent_start` 返回的持久化消息作为文本／技能指导的唯一投递 seam。它满足：

1. 投递保留在当前分支（经 `appendCustomMessageEntry` 持久化），后续回合可在原位读到。
2. 去重依据是保留对话中已投递的 `harness-guidance` 消息的 `details.entries`，resume／fork／reload 后仍准确（不依赖进程内集合）。
3. 指导是独立消息，不破坏 tool call／tool result 协议顺序。
4. 命中本身不启动额外模型轮次（不用 steering）。
5. 隔离的真实 `pi --print` 加载扩展、运行 `before_agent_start` 无错退出。

已明确放弃：临时的 `context` 钩子投递。它不持久化，会导致每次请求重复追加与前缀分叉，与保留／去重／缓存稳定目标相悖。

**剩余门槛（未实现，诚实标注）：** 同一轮内工具结果首次引入关键词的 mid-run 即时投递。这需要 Pi 在请求准备 seam 提供可验证的持久化即时投递；在公开接口确认支持前，文本指导采用回合起始粒度。不得用临时尾部重建、私有模块路径依赖或隐式强制续轮代替。

正则执行采用体量预算（段数／字符上限）+ 未完成报告：超预算时 `evaluateText` 返回 incomplete，规划器保留现有投递状态并报告未完成，绝不把未完成当作"无匹配"。**已知限制：** 单个灾难性回溯正则在同步执行下不可中断，真正的不挂死需要 worker 隔离执行；当前以体量预算与作者端的有界模式约定缓解，未实现单模式抢占。

缓存测试比较连续请求的消息序列和前缀；禁止以“模型输出正常”代替前缀稳定性证据。真实 provider 的 cacheRead/cacheWrite 可作为补充观测，不作为跨 provider 的必然保证。

## 14. 替换旧格式与范围

新格式直接替换 `policies`、`disabled`、`skillPrompts` 的配置解释。包内默认规则、示例、创建流程、状态展示、consolidation 及测试统一转向 `rules`，不维持两套长期运行语义。

发布按破坏性格式变更处理。实际用户文件仅在用户授权后，根据完整预览替换；提供的是显式重新创作／写入，不是运行时兼容加载或自动发现迁移。旧格式保持原始字节，并得到明确格式诊断。

迁移预览逐项说明：

- 可表达为新 `skill`、`bash`、`text` 规则的内容及身份。
- 从 system prompt 转为带来源对话消息的指导语义变化。
- 适合留在项目指导、技能说明或独立验证流程的要求。
- 旧 `observe` 仅记录，与新省略 action 后向模型提供消息的差异。
- 旧 output／artifact、其他工具和参数路径检查的后续归属。

本设计不自动修改 Open DeskOS、全局 agent 配置、Memory 或现有项目指导，也不创建通用事件系统、任意代码执行器、模型幻觉消除机制或全局安全隔离层。

## 15. 设计反思与定稿原则

这次统一的不是字段外观，而是身份、状态、来源和覆盖规则。Skill 名称、Bash 正则、Text 正则都承担匹配职责；它们针对的对象与运行时机不同，保持明确入口比通用 `kind + when` 更直接。

消息传递与执行条件分开：Bash 可以正常执行并提供指导，`confirm` 和 `block` 只增加本次调用的执行条件。Skill 与 Text 专注上下文，不承诺执行隔离。

可靠送达依靠可追踪的消息位置，而不是反复追加相同提示；缓存友好依靠保留已有前缀，而不是每次把提示重新移到尾部。追加式更新保留历史，代价是旧指导无法从模型已经看到的内容中撤回，这一限制应如实展示。

最终原则：

> 扁平存储，按身份覆盖，按对象匹配；匹配即提供指导，Bash 动作可选；新上下文尾部追加，既有上下文原位保留。
