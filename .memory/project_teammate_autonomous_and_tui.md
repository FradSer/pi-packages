`packages/teammate` is a real multi-agent team: teammates are autonomous child Pi processes that watch their own mailbox via a **shared state file** (`~/.pi/agent/teammate/<sessionKey>/state.json`, atomic tmp+rename writes) and decide when to close; the leader is always the current main session.

**Why:**
Earlier versions spawned one-shot workers the leader had to sleep-poll; the TUI panel used global key interception and broke pi's model selector. The redesign made workers fully autonomous (they read/reply via the shared file, post updates to `mailboxes["agent"]`, close on their own idle window) and moved ALL interaction into a full-screen console that owns input. The ecosystem (pi-subagents, pi-dynamic-workflows, etc.) is saturated with ephemeral "spawn → task → result" delegation; the distinctive gap was a *persistent team OS*: named roles (team-leader/worker/reviewer/specialist/observer), mailbox communication, a dependency-gated task board, and liveness — where teammates actually execute work.

**How to apply:**
1. **Autonomous spawn**: `teammate_spawn` default `background=false` BLOCKS until the worker closes itself and returns its report (no polling); `background=true` fires-and-forgets — the worker keeps watching its mailbox until it decides to stop. The guardian-loop prompt (spawner `buildAutonomousPrompt`) tells the worker to process its task, poll its mailbox, proactively message the leader (`mailboxes["agent"]`), and close on idle/explicit stop; hard `timeoutMs` (default 30 min, `DEFAULT_TIMEOUT_MS` in `src/index.ts`) is the safety cap — the worker is SIGKILLed and the task fails with a timeout reason. Exit semantics: exit 0 → task completed with stdout as result; non-zero → failed with stderr as error.
2. **Shared state file** (`src/statefile.ts`): session-scoped, atomic writes (write temp file + rename); parent publishes before spawn (and via `publishToStateFile()` on `teammate_send`/`assign_task`/etc. to reach running workers), `applyStateFile` merges worker-written replies/task updates back on exit. Workers must only touch their own mailbox + assigned task.
3. **Dependency gating**: tasks carry `blocks`/`blockedBy` (auto-maintained inverse edges in `src/state.ts`); spawn is rejected until every `blockedBy` task is completed or cancelled (`teammate_task_deps`).
4. **Worktree isolation**: `isolation="worktree"` runs the worker on branch `teammate/<taskId>` in `.pi/worktrees/teammate-<taskId>`; the diff is captured into the task result and the worktree + branch are removed on completion. Safe to re-create for the same taskId after cleanup (retry).
5. **Liveness & Live Polling**: teammates flip `idle`/`running` (with `currentTaskId`); `teammate_list` shows it. To make worker progress visible mid-execution, the extension polls the shared state file every 5s (`ensureLivePoll()`) while any worker is running, merging updates to memory and refreshing the widget so inbox alerts and task results appear in real time.
6. **Cost accounting**: worker usage (tokens/cost) is parsed from the child's JSONL output into `task.spawn.usage` — see [[pi-cli-print-json-usage]] for the `--print --mode json` parsing recipe.
7. **Notification consumption**: `markTaskNotificationsRead(taskId)` marks the "New task:" assignment message read when the task starts (spawn or `in_progress`) — the footer/panel unread count reflects real attention-needing messages, not stale assignment history.
8. **Management tools**: `teammate_remove` (refuses running worker unless force), `teammate_cleanup` (prune finished tasks / one task), `teammate_reset` (wipe board, refuses running), `teammate_update_model` (change teammate model pattern for next spawn). `session_shutdown` removes the session's state dir; `session_start` sweeps dirs older than 7 days.
9. **Leader = main session**: `teammate_register role="team-leader"` is rejected; `teammate_assign_task` / `teammate_broadcast` are always available (from `"agent"`). `teammate_read_mailbox name="agent"` reads the leader inbox without a registered teammate.
10. **TUI (no global interception)**: a passive `setWidget` above the editor shows teammate rows (colored, `(teammate)` label for worker role, `● running task_x` / `○ idle`) plus an alert `N message(s) to you from teammates` (with preview of the latest message). `/teammate` opens a full-screen console (`ctx.ui.custom`, owns input) styled matching `@packages/btw/` (`BtwOverlayStyle`: top/bottom borders, accent header, dim shortcuts footer). It supports ↑/↓ select, Enter open, `r` reply, Esc back/close, `x` stop, `q` close. A teammate page shows unread + tasks sections and the FULL conversation (`←` received / `→` sent, merged by time); the tasks section renders the agent's full running content via `buildTaskSection` — task description, spawn lifecycle/usage, `--- Worker output ---`/`--- Worker stderr ---`, result/error.
11. Worker display role: `worker` renders as `(teammate)` (`displayRole`).
12. **Message read status & leader read receipts**: leader inbox (`/teammate` → inbox) displays `✓ received` / `● unread`; teammate conversation page displays `✓ leader received` / `○ leader pending` for sent messages (sender perspective), and `✓ read` / `● unread` for received messages. Reading messages triggers `syncReadFlagsToFile()`, which writes leader read receipts (`read: true`) back to the shared state file for workers to observe. When a worker process exits, `finish()` writes back merged state so read receipts persist on disk. `applyStateFile` merges state while preserving existing `read: true` flags, preventing worker file writes from rolling back leader receipts.
