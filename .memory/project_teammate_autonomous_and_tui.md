`packages/agent-teams` is a real multi-agent team: the current Pi session is the leader and sole `state.json` writer. Teammates are autonomous child Pi processes that read the leader-owned snapshot and append identity-bound events to their own outboxes under `~/.pi/agent/teammate/<sessionKey>/events/`.

**Why:**
Earlier versions spawned one-shot workers the leader had to sleep-poll; the TUI panel used global key interception and broke pi's model selector. The redesign made workers fully autonomous (they read/reply via the shared file, post updates to `mailboxes["agent"]`, close on their own idle window) and moved ALL interaction into a full-screen console that owns input. The ecosystem (pi-subagents, pi-dynamic-workflows, etc.) is saturated with ephemeral "start → task → result" delegation; the distinctive gap was a *persistent team OS*: named worker/reviewer/specialist/observer roles, mailbox communication, a dependency-gated task board, and liveness — where teammates actually execute work.

**How to apply:**
1. **Autonomous runs**: `teammate_start_task(taskId)` is always asynchronous and returns the pid/run identity immediately; the main session continues coordinating. `teammate_wait` is the sole explicit gather barrier. The worker keeps watching its inbox until it decides to stop. The guardian-loop prompt (spawner `buildAutonomousPrompt`) tells the worker to process its task, poll its inbox, message peers/the leader, and close on idle/explicit stop; hard `timeoutMs` (default 30 min, `DEFAULT_TIMEOUT_MS` in `src/index.ts`) is the safety cap — the worker is SIGKILLed and the task fails with a timeout reason. Exit semantics: normal code 0 → success; non-zero, timeout, or signal → failure.
2. **Leader-owned state + worker outboxes** (`src/statefile.ts`): parent atomically publishes `state.json` before spawn and after leader-side updates. Every spawn receives a new `runId`; each worker has a per-run append-only JSONL outbox. `applyWorkerEvents()` drains complete records, validates worker identity, run ownership, recipient, task ownership, and event ID, then applies valid events in leader memory before publishing the next snapshot. A completed run persists its final snapshot before its outbox/cursor/replay metadata are compacted. This prevents stale full-state writes, stale earlier runs, and read-receipt rollbacks.
3. **Dependency gating**: tasks carry internal `blocks`/`blockedBy` inverse edges in `src/state.ts`; public creation accepts only `blockedBy`, and start is rejected until every blocker is completed or cancelled. Dependencies are immutable after creation; there is no public graph-mutation tool.
4. **Worktree isolation**: `teammate_start_task({ taskId, isolation: "worktree" })` runs the worker on branch `teammate/<taskId>` in `.pi/worktrees/teammate-<taskId>`; the diff is captured into the task result and the worktree + branch are removed on completion. Failed tasks restart only with explicit `retry: true`, which creates a fresh run identity.
5. **Liveness & Event Draining**: teammates flip `idle`/`running` (with `currentTaskId` + `currentRunId`); `teammate_list` shows it. Every 5s (`ensureLivePoll()`), the leader drains validated worker outboxes and refreshes task details. A run succeeds only after normal exit code 0; non-zero exit, timeout, SIGTERM/SIGKILL, or worker-reported failure fail it. The passive widget uses an independent braille spinner and displays a short task title, not the raw task ID.
6. **Cost accounting**: worker usage (tokens/cost) is parsed from the child's JSONL output into `task.spawn.usage` — see [[pi-cli-print-json-usage]] for the `--print --mode json` parsing recipe.
7. **Notification consumption**: `markTaskNotificationsRead(taskId)` marks the "New task:" message read when `teammate_start_task` begins the task — the footer/panel unread count reflects real attention-needing messages, not stale assignment history.
8. **Resource-oriented public surface**: leader tools are `teammate_register`, `teammate_list`, `teammate_configure`, `teammate_remove`, `teammate_message`, `teammate_inbox`, `teammate_create_task`, `teammate_list_tasks`, `teammate_start_task`, `teammate_wait`, `teammate_cancel_task`, and `teammate_cleanup`. Workers get only `teammate_message`, `teammate_inbox`, and `teammate_report`. Do not reintroduce assign/update/dependency-mutation/spawn/reset/model-update tools, compatibility aliases, or an action-dispatch mega-tool. `teammate_remove` refuses a teammate with any assigned/in-progress task; `teammate_cancel_task` stops the run first. Cleanup prunes all terminal tasks only.
9. **Leader = main session**: the leader is not a `Teammate` role — `TeammateRole` excludes `team-leader`. `teammate_create_task` creates and assigns in one action; `teammate_message to="all"` replaces broadcast, and `teammate_inbox` reads the leader inbox without a registered teammate.
10. **TUI (no global interception)**: a passive `setWidget` above the editor shows teammate rows (colored, `(teammate)` label for worker role, animated task title + `working...` / `○ idle`). It does not duplicate leader mailbox messages; `teammate_inbox` returns them in the current session conversation. `/teammate` opens a full-screen console (`ctx.ui.custom`, owns input) styled matching `@packages/btw/` (top/bottom borders, accent header, dim shortcuts footer). It supports ↑/↓ select, Enter open, `r` reply, Esc back/close, `x` stop, `q` close. A teammate page shows unread + tasks sections and the FULL conversation (`←` received / `→` sent), merged by time. The tasks section renders the agent's full running content via `buildTaskSection` — task description, spawn lifecycle/usage, `--- Worker output ---`/`--- Worker stderr ---`, result/error.
11. Worker display role: `worker` renders as `(teammate)` (`displayRole`).
12. **Unified communication + receipts**: `teammate_message` is the sole send tool: the leader targets a registered teammate or `all` (optional role filter); a worker targets one peer or `agent` (the main session). `teammate_inbox` is the sole inbox tool: in leader mode it drains current worker outboxes then reads `agent`; in worker mode it reads the identity-bound worker inbox and emits receipt events for newly consumed messages. Worker inbox scans its own outbox to suppress receipt-pending duplicate delivery. The TUI has no aggregate message-count row. Reading messages triggers `syncReadFlagsToFile()`, which writes leader read receipts (`read: true`) back to the shared state file for workers to observe. Blocking completion and `teammate_wait` consume only matching task messages after their results are delivered; unrelated messages remain unread. When a worker process exits, `finish()` writes back merged state so read receipts persist on disk.
13. **Orchestration guidance & prompts**: the extension injects leader guidance covering when to delegate, role prompts, task handoff fields, parallel fan-out + `teammate_wait`, dependencies, review evidence, failure handling, and synthesis. `Teammate.prompt` is persisted, shown in details, and included under `ROLE PROMPT` in every worker process. A worker receives `WORKER_GUIDANCE`, registers **only** `teammate_message`, `teammate_inbox`, and `teammate_report`, and returns before leader lifecycle/UI/board tools register. Role defaults are worker=`read,bash,edit,write`, reviewer/specialist=`read,bash`, observer=`read`; explicit teammate tools override those defaults and capability tools stay appended.
14. **Safe coordination boundary**: this is a reliable collaboration protocol, not an OS sandbox, because workers still run under the user account. Pending-task self-claim is intentionally not enabled: Claude's task claiming uses file locking; atomic rename prevents partial snapshots but does not provide a claim lock. Add a real cross-process lock before allowing multiple workers to claim pending tasks. Plan approval and task-completion hooks likewise need explicit state-machine design before implementation.
