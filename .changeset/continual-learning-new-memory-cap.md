Bound how many new Memory files one automatic task may create. The private debug logs confirm this is a general pattern, not one project: across all scopes, 17 automatic batches wrote three or more Memory files (six, six, five, five fours, nine threes) and 19 stored plans contain three or more `newMemories`, mostly with `no-durable-memory-evidence` but routed to Memory by an agent `learn` request or an observed indexed-Memory read. The `hud-playground` case (`batch_67abf737...`, four files, `mode=automatic`, `input.source=current-session`) is one of them; an earlier plan there held six. The existing 16-candidate plan limit and same-batch Jev novelty only compared the current batch, so small batches accumulated indefinitely. `maxNewMemoriesPerRun` in the unified `continual-learning.json` (default `2`, valid `1..16`, invalid values fail closed) caps newly created files after full structural and semantic review: an over-limit automatic plan is saved as a reviewable proposal and reports the exact count and limit, with no Memory file or applied mutation receipt. Only `plan.newMemories` counts — verifying against all 128 stored plans, counting total operations instead would flip the decision on eight batches that also rewrite or delete existing records. Rewrites, deletes, propose policies and explicit `/memory` requests are exempt, and later Harness/AGENTS.md planners do not run from a held Memory plan.

A held plan is now reported honestly in the terminal. The first cap implementation reused the `semanticProposal` hold path, so the memory attempt settled as `proposed` with `operations: 0` and the result row fell through to the quiet zero-write branch — reporting `no changes written` plus `N frozen entries were checked; mirrors, indexes and consistency were verified` even though the parent had actively held a grounded plan. A real `git-agent-cli` run (`batch_a0ef7c...`, 11-11) showed the `ui:notify` hold and that result line 25 ms apart from the same receipt. The parent now records a `new-memory-cap-hold` routing marker on the receipt; `learningSummarySubject` reports `new Memory plan held by per-run limit; proposal saved for review` and the zero-write "no changes / verified" expansion is suppressed for it. Normal zero-write runs are unchanged.
